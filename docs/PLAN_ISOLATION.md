# プラン分離とテスト範囲

**目的:** プラン固有の変更が他プランに波及しにくく、テスト範囲を最小に保つ。

## 原則

アプリは **共用の土台（マッチ・チャット・日程）** と **プラン専用の部屋（機能）** でできている。

| 層 | 例 | 変更時の影響 |
|---|---|---|
| プラン専用 | スキルチェック、伴走シート、コーチング専用タブ、月次申し込み | **そのプラン中心**でテストすればよいことが多い |
| 共用 | マッチ作成・一覧・入場、チャット、日程調整、権限の共通処理 | **他プランのスモークも必須** |

## プラン判定の正本

1. **マッチに紐づく `programId` → そのプログラムの `plan`**
2. ユーザー単位 API は、企業レジストリの代表プランではなく **該当プランのプログラムが存在するか** で判定する
3. `programId` が無いレガシーマッチは、企業レジストリプランのプログラムへだけ寄せる（**別プランの最古プログラムへ落とさない**）

## 機能フラグ

個別伴走の成果物（FTA / スキルチェック / PDCA / 振り返り / ライフライン / サマリー）は:

- UI（タブ表示）だけでなく
- **API でも同じ ON/OFF（`planFeatureOverrides`）を見る**

OFF なら画面に出ないだけでなく、API も `plan_disabled` になる。

## 変更時のテスト範囲（運用ルール）

### A. プラン専用レイヤーだけ触ったとき

対象例: `skill-check-*` / `companion-*` / `coaching-*`（コンテンツ） / `monthly-session-*`

**テスト:** そのプランの主要導線 + 権限（本人 / 上司 or パートナー / 管理者）

他プランのフル回帰は不要。不安なら該当プランと共用導線の有無だけ確認。

### B. 共用レイヤーを触ったとき

対象例: `match-access` / `match-repository`（一覧・作成） / `listMatchesForRole` / チャット・日程の共通 API / `effective-app-settings` の共通解決

**テスト（必須スモーク）:**

1. 職場活性: マッチ入場・チャット or 日程のどれか1つ
2. 個別伴走: マッチ入場 + スキルチェック or シート1つ
3. コーチング研修: 未割当ルームが出ないこと / ルーム入場
4. 月次セッション: 申し込み入口が出る/出ないがプランどおりであること

### C. 1社に複数プログラムがあるとき

追加で確認:

- プログラムごとのマッチで、タブ・API がそれぞれのプランになること
- 上司マッチ（CLIENT_ADMIN を partner）が **個別伴走以外では作れず・見えず・入れない**こと
