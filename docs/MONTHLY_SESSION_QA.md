# 月額プラン（セッション申し込み）— 2人デバッグ手順

**対象機能:** マッチなしの「セッション申し込み」（プラン ID: `monthly_session`）  
**想定人数:** モチベイジ2名（管理者兼クライアント / パートナー、または役割を交代）  
**環境:** staging（`https://companion-scheduling--motive-iji-cloud-1e300.asia-east1.hosted.app`）  
**注意:** staging は本番と同じ Firestore を参照します。テスト用企業・ユーザーを使い、実クライアント企業のデータは触らないでください。

関連: 全体の受入要件は `docs/TEST_REQUIREMENTS.md`。本ドキュメントは月額プランの追加分に特化します。

---

## 0. 役割分担（例）

| 担当 | 推奨ロール | 主な作業 |
|------|------------|----------|
| **A** | ADMIN（＋必要ならテスト用 CLIENT） | 企業・プログラム・対象パートナー・上限・受付時間の設定。クライアント予約の確認 |
| **B** | PARTNER（月額対象にチェック済み） | プロフィール・空き枠登録／取り下げ。予約後の詳細・チャット |

2アカウントでブラウザを分ける（通常 + シークレット、または別ブラウザ）。

---

## 1. 事前セットアップ（初回のみ / 再テスト時）

チェックしながら進めてください。

### 1.1 テスト用企業

- [ ] `/admin/settings` でテスト用企業がある（なければ追加）
- [ ] 企業プランに **月額プラン（セッション申し込み）** を選択して保存  
  → 保存後、月額プログラムが自動作成される想定  
  → **入口の表示条件:** 企業代表プランが月額、またはメンバーの参加プログラムに月額が含まれること（他プラン企業に月額プログラムが同居しているだけでは出ない）
- [ ] または企業詳細 `/admin/companies/{companyId}` → **導入プログラム** から「月額プラン（セッション申し込み）」を追加し、対象メンバーの参加プログラムにチェック

### 1.2 月額上限・受付

- [ ] 企業のプログラム設定で **月あたり上限** を設定（テストしやすいよう最初は `2` など低め推奨）
- [ ] `/admin/monthly-session` で  
  - 受付曜日・時間帯  
  - **対象パートナー**（B のアカウント）にチェック  
  を保存

### 1.3 ユーザー

- [ ] テスト用 CLIENT の `companyId` が上記テスト企業になっている
- [ ] CLIENT が月額プログラムに参加している（プログラム追加時に自動参加される想定。見えない場合は企業メンバーの参加対象を確認）
- [ ] PARTNER が `/sessions-booking/partner` を開ける（対象外だと 403）
- [ ] PARTNER の Zoom / Meet がプロフィールに登録済み（確定メール・詳細画面の会議リンク用）

### 1.4 ダッシュボード入口

- [ ] CLIENT ホームに「セッション申し込み」入口が見える
- [ ] PARTNER ホームにも同様の入口が見える（対象パートナーのみ）

## 2. パートナー：空き枠の登録と取り下げ

| # | 手順 | 期待結果 |
|---|------|----------|
| P1 | `/sessions-booking/partner` でフルネーム・経歴・自己紹介・対応種別を保存 | 保存成功メッセージ。再読込後も残る |
| P2 | **当月**（日本時間で既に始まっている月）の日付で 30 分枠を複数追加 | 「登録済みの空き枠」に表示される |
| P3 | 未予約の枠で **取り下げ** → 確認ダイアログで OK | 一覧から消える。CLIENT 側の空き候補からも消える |
| P4 | 48 時間以内の枠を追加しようとする | 登録されない／無視される（48時間前ルール） |
| P5 | 受付時間外・休業曜日の枠を追加しようとする | 登録されない |

**ポイント:** 取り下げできるのは **まだクライアントに取られていない空き枠のみ**。予約されると空き枠一覧から消え、セッション一覧に移る。

---

## 3. クライアント：予約フロー

| # | 手順 | 期待結果 |
|---|------|----------|
| C1 | `/sessions-booking` を開く | 今月の利用回数（例: `0 / 2`）が表示される |
| C2 | 種別（カウンセリング等）→ 空き枠 → パートナー選択 → 予約 | 「予約が完了しました」。一覧に確定が表示される |
| C3 | 予約直後のメール（CLIENT / PARTNER / 管理者宛） | 件名に確定・ICS。本文の開始・終了が **日本時間**。Google / Outlook 追加リンクあり。`session.ics` 添付 |
| C4 | `/sessions-booking/{bookingId}` | 会議リンク、カレンダー追加ボタン、.ics ダウンロードが出る |
| C5 | **翌月**の空き枠だけパートナーが先に登録してある場合 | クライアント側には **翌月1日（JST）になるまで** 出ない／予約不可 |
| C6 | 上限まで予約したあとさらに予約しようとする | 文言: 「月毎の上限を超過しました。…人事担当者様へご連絡ください」。新規予約 UI が閉じる |

### キャンセル

| # | 手順 | 期待結果 |
|---|------|----------|
| X1 | 開始 24 時間以上前に CLIENT または PARTNER がキャンセル | 成功。空き枠がパートナー側に戻り得る |
| X2 | 開始 24 時間を切ってキャンセル | 管理者以外は不可 |

|---|------|----------|

## 6. パートナー予定登録リマインド（メール）

自動送信は **日本時間の毎月 12日 / 27日** のみ（GitHub Actions → `/api/cron/monthly-partner-reminder`）。

| 日 | 内容 |
|----|------|
| **12日** | 当月 15日〜月末 の空き枠登録を促す |
| **27日** | 翌月 1日〜15日 の空き枠登録を促す |

デバッグ時:

- [ ] Actions の `cron-monthly-partner-reminder` を **workflow_dispatch** で手動実行できる（該当日以外は `skipped: not_reminder_day`）
- [ ] 該当日に実行すると対象パートナーにメールが届く（同日再実行は `already_sent` で二重送らない）

## 7. 2人での回し方（短時間パス）

推奨の最短スモーク（30〜45分）:

1. **A**: テスト企業・上限=2・対象パートナー=B を確認
2. **B**: プロフィール保存 → 当月の空き枠を 3 本登録 → うち 1 本を **取り下げ**
3. **A（CLIENT）**: 残った枠で 1 件予約 → メール・ICS・詳細画面のカレンダーを確認
4. **B**: セッション一覧に予約が出る／空き枠一覧には無いこと
5. **A**: もう 1 件予約 → 上限に達した表示・これ以上予約できないこと
6. **両者**: 可能なら「翌日以降の枠」でキャンセル（24時間ルール）を確認

不具合報告フォーマットは `docs/TEST_REQUIREMENTS.md` セクション 8 に合わせる。

## 8. よくあるつまずき

| 現象 | 確認すること |
|------|----------------|
| CLIENT に入口が無い | 企業に `monthly_session` プログラムがあるか／参加（enrolled）されているか |
| PARTNER が入れない | `/admin/monthly-session` の対象パートナーチェック |
| 空き枠が見えない | 48時間後以降か／当月1日以降か／受付時間・種別が一致しているか／取り下げ済みでないか |
| メールが来ない | Resend 設定・迷惑メール・ユーザーに通知用メールがあるか |
| 上限に達しない／すぐ達する | プログラム ID ごとの上限、キャンセル済みはカウント外、月キーは JST |
